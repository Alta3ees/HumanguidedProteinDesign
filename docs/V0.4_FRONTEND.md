# v0.4 Interactive Research Workspace

v0.4 turns HGD's persistent scientific archive into a local interactive workspace.

The canonical source of truth remains:

```text
data/projects/<project>/design_archive.json
```

The React frontend never edits archive JSON directly. Scientific state changes go through the local FastAPI API and validated Python domain/action layer; the browser mainly presents and organizes the archived scientific state.

## Architecture

```text
design_archive.json + project-local scientific files
                    |
                    v
        HGD Python archive/actions
                    |
          PyRosetta / PyMOL
                    |
                    v
       local FastAPI (127.0.0.1)
                    |
                    v
 compiled React + TypeScript workspace
```

HGD does not require a hosted service, account, or cloud database for normal operation.

## Current workspace features

### Project and lineage

- create and switch local projects;
- register starting/imported/generated designs;
- radial parent/child design map;
- clicking a node selects it and updates the right-side summary without leaving the main view;
- the full scientific record opens only when the user explicitly chooses **Open full scientific record**;
- sequence-derived child creation without rewriting history;
- accepted, rejected, deferred, active, and deprioritized provenance.

### Structures

- attach PDB, CIF/mmCIF, ENT, and PQR structures from the design's full scientific record;
- associate multiple structural hypotheses with one design;
- retain source/method/confidence metadata;
- launch selected structures in local PyMOL;
- delete copied project-local structures while preserving historical evidence.

### PyRosetta design tools

- baseline score of the current structure;
- one hypothesis-driven point mutation;
- matched local repacking/minimization and parent-relative ΔScore comparison;
- selected Rosetta score-term breakdown;
- structural-neighborhood context;
- saturation scan of all 19 alternative amino acids at one position;
- Accept / Defer / Reject decision directly after mutation evaluation;
- automatic child-node creation for every evaluated mutation;
- explicit Design A vs Design B comparison using scores already archived on the selected designs.

HGD checks that the selected structure sequence is compatible with the design before mutation/scanning operations.

Mutation-generated child designs automatically receive their own archived PyRosetta mutation-evaluation score. Other designs become eligible for project-level A/B comparison after their structure is scored explicitly from the full scientific record.

The comparison UI always names **Design A** and **Design B**, reports `Score(B) - Score(A)`, shows the score source/date used for each design, and does not silently assume WT as the reference.

### Evidence and scientific files

Evidence categories are:

```text
computational
experimental
literature
note
```

Files are copied into the local project and referenced using project-relative paths where possible.

Native previews currently recognize common scientific formats including:

- FASTA;
- CSV/TSV/XLSX;
- JSON;
- Rosetta `.sc` scorefiles;
- PDF;
- PNG/JPG/SVG/TIFF images;
- Markdown/text/log files;
- molecular structure files.

Unknown/raw instrument formats can still be archived as evidence even when HGD cannot preview them.

## Project context export

The workspace exposes one project-level Markdown export:

**Export context for LLM (.md)**

It generates:

```text
PROJECT_CONTEXT.md
```

The file contains a readable project overview and detailed scientific records followed by the complete archive JSON in a fenced appendix. It is intended as a portable snapshot for an LLM, collaborator, or downstream text-based workflow.

`PROJECT_CONTEXT.md` is generated from the archive; it is not a second source of truth.

## Run locally

For normal use, activate the environment and run one command:

```bash
conda activate human-guided-protein-design
hgd
```

`hgd` builds the frontend when necessary, starts the local backend, serves the compiled browser workspace, and opens the local application at `http://127.0.0.1:8000`.

A second terminal is **not required** for normal scientific use.

### Frontend development only

Developers who specifically need Vite hot reload can still use:

```bash
cd frontend
npm install
npm run dev
```

That is a developer workflow rather than the end-user launch path.

## Projects root

Default:

```text
data/projects/
```

Override locally with:

```bash
HGD_PROJECTS_ROOT=/path/to/projects hgd
```

## Validation

Python:

```bash
python -m pytest -q
```

Frontend:

```bash
cd frontend
npm install
npm run build
```

## v0.4 boundary

The web workspace is now the primary HGD user interface. CLI scripts remain useful for validation and direct workflows, but new scientist-facing capabilities should normally reuse the canonical archive/scientific logic and then be surfaced clearly in the workspace.
